# MERN Starter 宪章（中文译本）

## 核心原则

### I. 全栈 JavaScript 一致性
- 所有产品代码必须保持在标准 MERN 技术栈内：MongoDB+Mongoose、Express API、React 客户端以及由 `index.js` 编排的 Node.js 服务。
- 共享数据契约位于 `models/`，必须作为 API 负载、服务器校验和 React 数据访问辅助方法的唯一真源。
- 客户端与服务端构建脚本必须在 `package.json` 指定的 Node.js 与 npm 版本下编译通过，方可接受变更。
理由：统一的技术栈能降低上下文切换，便于排查 Heroku 部署问题，也让任意工程师都能跨层交付。

### II. API 合同优先交付
- 每个特性在合并任何路由或组件代码前，必须在 `specs/<feature>/contracts/` 中定义或扩展 REST/JSON 合同（请求、响应与错误）。
- 合同必须包含认证要求及适用时的分页或限流规则，plan.md 需给出链接。
- Pull Request 在获批前必须附上更新后的 swagger/Markdown 片段或证明合同行为的测试。
理由：合同优先能保护 React 客户端免受后端波动影响，并让外部集成（Stripe、OAuth）尽早得到验证。

### III. 测试驱动的用户旅程
- spec.md 中记录的每个用户故事必须至少拥有一个在实现前会失败的自动化测试（`tests/` 下的后端集成测试或 React Testing Library 等）。
- 关键流程（认证、计费、数据持久化）必须覆盖成功与失败路径；仅提交单元测试将被拒收。
- 在合并前必须运行 CI（或本地 `npm test`），任何失败都要在解决或获得维护者豁免后才能发布。
理由：全栈代码库的回归风险最高；强制旅程级测试可保证安全部署并记录意图。

### IV. 安全认证与数据治理
- 所有密钥（OAuth、Stripe、会话盐值）必须通过环境变量管理，禁止硬编码；新增密钥必须同步更新 `.env.example`。
- 通过 Express 路由收到的输入必须在触达 MongoDB 前完成校验和净化，Passport 策略需执行最小权限原则。
- 依赖升级必须通过 `snyk test`，或在 tasks.md 中记录缓解计划；若未修复关键 CVE，视为回滚理由。
理由：应用会处理支付数据以及社交登陆令牌，一旦密钥或依赖处理不当，用户与平台信任都会受到威胁。

### V. 运维就绪与可观测性
- 特性开发必须保持 `npm run dev`、`npm run client` 与 Heroku `Procfile` 可部署；禁止无明确清理任务的长期 feature flag。
- 所有服务必须输出结构化日志（请求 ID、用户 ID、动作）并在行为偏离预期时暴露关键健康指标或告警。
- 在推广至生产前，部署计划必须记录回滚步骤及数据迁移（如有）。
理由：持续的运维卫生可帮助小团队快速定位事故并达到可用性承诺。

## 平台与安全约束
- **运行环境**：Node.js 10.12.0 + npm 6.4.1 负责服务端构建，`client/` 应用使用 React 18+，存储使用兼容 MongoDB Atlas 的 Mongoose ODM。
- **认证**：Google/GitHub 的 Passport 策略必须保持为主认证手段；若引入其他方式必须经过安全评审。
- **支付**：Stripe 交互必须经过专用服务层，以隔离涉及 PCI 的代码；非生产运行必须使用测试密钥。
- **工具链**：Prettier 为唯一格式化工具，CI 必须执行 Snyk 扫描，除非治理批准，Heroku 是唯一权威部署目标。
- **配置**：环境配置必须通过 `config/` 帮助模块传递，确保服务端和客户端共享一致的特性开关，并保证密钥不会被打包到客户端。

## 交付流程与质量关卡
- 特性流转顺序为 `/speckit.plan` → `/speckit.spec` → `/speckit.tasks`；每份产物都必须说明如何满足上述原则。
- plan.md 中的 Constitution Check 必须在 Phase 0 研究前通过；若规格不满足，则需缩小范围或申请治理豁免。
- 每份计划必须说明将修改哪些代码目录（`client/` 或后端）以及共享模型的复用方式，以避免偏差。
- spec.md 必须列出相互独立的用户旅程与明确的验收测试；tasks.md 必须保持用户故事隔离，便于增量交付。
- 在合并前，评审者需确认合同、测试、安全要求及运维文档均已更新；缺项视为阻塞。

## 治理
- 本宪章优先级高于临时约定；若需偏离，必须以 RFC 形式链接到相关 spec.md，并取得两位维护者批准。
- 修订流程需包含：(1) 动机与影响摘要，(2) 更新的同步影响报告，(3) 在 Git 历史中记录的版本提升理由，(4) 模板与运行文档同步确认。
- **版本策略**：移除/替换原则或治理规则视为 MAJOR；新增原则或扩展章节为 MINOR；仅澄清或修饰为 PATCH。
- 每季度进行一次合规审查，抽检至少两个最近特性，确保合同、测试与运维产物符合规则；发现的问题需转换为任务。
- 运行指引（README、quickstart、agent 文件等）必须引用当前原则；贡献者有责任在发现偏差时提出提醒。
